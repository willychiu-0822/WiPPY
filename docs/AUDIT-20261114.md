## 2. 逐條說明

### W-01｜P0（待確認線上設定）｜程式品質／安全｜內部 harness 端點可用空白 header 通過

- **證據**
  - `backend/src/routes/internal/harness.ts:12-13`：`if (secret !== (process.env.INTERNAL_HARNESS_SECRET ?? ''))`。環境變數沒設時，比對對象是空字串。
  - `backend/src/routes/internal/harness.ts:18-34`：`userId`、`activityId`、`userMessage` 全部取自 request body，沒有再驗身分。
  - `.github/workflows/deploy.yml:63-75` 的 `env_vars` 沒有 `INTERNAL_HARNESS_SECRET`，也沒有 `CLOUD_TASKS_*`；線上是否另外手動設定，repo 內看不出來。
  - 實測（本機、未設該變數）：
    ```
    不帶 header              -> 401 {"error":"Unauthorized"}
    帶 x-harness-secret: (空) -> 400 {"error":"Missing required fields"}   ← 已通過驗證
    ```
  - 對照：Hub 的同類端點寫法是對的，`backend/src/hub/http/internalRouter.ts:14-15`（`if (!secret || ...)`）。
- **影響**：若線上沒設這個變數，任何人都能對公開的 Cloud Run 網址觸發 AI 規劃（花模型額度），並在知道 `activityId`／`userId` 的情況下以該使用者名義寫入推播企畫。
- **建議修法**：沒設密鑰一律 401（照 `internalRouter.ts` 的寫法）；比對改用 `crypto.timingSafeEqual`；把 `INTERNAL_HARNESS_SECRET` 放進部署流程（見 W-04）。先用 `gcloud run services describe` 確認線上現值。
- **驗收標準**
  1. 新增測試：未設變數時，不帶 header、帶空 header、帶任意值，三種都回 401。
  2. 線上對 `/api/internal/harness/run` 帶空白 `x-harness-secret` 回 401。
  3. 部署流程裡看得到這個變數的來源（Secret Manager 或 GitHub secret）。

### W-02｜P1｜程式品質／安全｜舊後台 API 的擁有者檢查會放行

- **證據**
  - `backend/src/middleware/auth.ts:33-37`：`if (ownerUserId && decoded.uid !== ownerUserId)`，沒設 `OWNER_USER_ID` 時不檢查，任何有效 Firebase 帳號都過。這個 middleware 保護 `/api/groups`、`/api/broadcast`、`/api/activities`、`/api/agent`、`/api/send-logs`。
  - `backend/src/routes/webhook.ts:18`：`process.env.OWNER_USER_ID!`，沒設時群組會以 `userId: undefined` 寫入。
  - 同一件事 Hub 是擋下來的：`backend/src/hub/http/routes.ts:21-27`。兩邊行為相反。
  - `deploy.yml:63-75` 沒帶 `OWNER_USER_ID`；`docs/agent-hub-setup-guide.md:17-30` 要人手動 `gcloud run services update`。
- **影響**：一旦那個手動設定被漏掉或被覆蓋，加上登入頁開著 Google 登入（W-06），任何 Google 帳號都能呼叫廣播 API。
- **建議修法**：正式環境沒設 `OWNER_USER_ID` 時，啟動就報錯結束（或所有 `/api/*` 回 503）；舊 API 改用 Hub 的 `hubAuth({ allow: ['owner'] })`，只留一套驗證。
- **驗收標準**：未設 `OWNER_USER_ID` 且 `K_SERVICE` 存在時，`/api/groups` 帶任意有效 token 回 503 或 403，有測試覆蓋；`webhook.ts` 不再有 `!` 斷言。

### W-03｜P1｜程式品質／安全｜`/scheduler/tick` 沒有任何驗證

- **證據**
  - `backend/src/routes/scheduler.ts:9-17`：`router.post('/tick', ...)` 沒有檢查任何 header；`backend/src/app.ts:32` 掛在 Hub 路由之前，所以 Hub 的 `schedulerSecret` 管不到它。
  - `backend/src/routes/scheduler.ts:15`：失敗時把 `String(err)` 原文回給呼叫端。
  - `backend/src/hub/http/schedulerRoutes.ts:17-18`：`if (secret && ...)`，`SCHEDULER_SECRET` 沒設時 `hub-tick`、`hub-quota`、`hub-cleanup` 也全開。
- **影響**：外人可以不停打這個端點，每打一次就全撈一次待發訊息（W-10），吃 Firestore 讀取費用；`hub-cleanup` 若密鑰漏設則能被外人觸發清資料。
- **建議修法**：`/scheduler/tick` 套用同一個 `schedulerSecret`；密鑰沒設時在正式環境一律拒絕。更好的做法是 Cloud Scheduler 用 OIDC token，後端驗 audience，不再用共用密鑰。
- **驗收標準**：不帶密鑰打 `/scheduler/tick` 與 `/scheduler/hub-*` 都回 401（含未設密鑰的情況），有測試；回應內容不含錯誤原文。

### W-05｜P1｜易用性／文案｜「確認排程」把給模型的指令當成使用者的話

- **證據**
  - `frontend/src/components/AgentChatPanel.tsx:237`：按鈕 `onClick` 送出的字串是「確認排程。請立即輸出純 JSON 陣列，不可有任何說明文字或 markdown code fence，格式：[{"content":"...","targetGroups":["all"],"triggerValue":"YYYY-MM-DDTHH:MM:SS+08:00","sequenceOrder":1},...]」。
  - `frontend/src/components/AgentChatPanel.tsx:108`：`send()` 會把這段原文加進對話，以使用者的泡泡顯示。
- **影響**：新手按下綠色的「✅ 討論好了，確認排程」，畫面上卻出現一長串自己沒打過的程式格式。這正是產品原則要避免的「AI 味」，也讓輸出格式的規則散在前端字串裡，改格式要改兩邊。
- **建議修法**：前端只送意圖（例如 `{ action: 'confirm_schedule' }`），格式要求由後端 `harnessOrchestrator` 加進 prompt；對話裡只顯示「就照這樣排」之類的短句。
- **驗收標準**：按下按鈕後，對話中使用者那一則不含 `JSON`、`markdown`、`{`、`triggerValue` 任一字樣；`frontend/src` 內搜尋不到「純 JSON 陣列」；既有 `AgentChatPanel.test.tsx` 補上這條斷言。

### W-06｜P1｜易用性／流程｜登入頁第一個按鈕通往死路

- **證據**
  - 截圖：`docs/audit-20261114-evidence/login-mobile.png`、`login-desktop.png`。最上面、最顯眼的是「使用 Google 繼續」。

  - 登入成功後由 `frontend/src/hub/RoleGate.tsx:11-13` 顯示「此帳號沒有 WiPPY 存取權限」。

- **建議修法**：擁有者實際用哪一種就只留哪一種當主要動作；另一種收成次要連結。若保留 Google，在 Firebase 端用 blocking function 或白名單擋掉非擁有者，不要讓人登入成功後才擋。
- **驗收標準**：登入頁只有一個實心主按鈕；用一個不在名單內的 Google 帳號測試，在登入當下就看到說明，且 Firebase Auth 不會多出該使用者。

- **證據**

### W-10｜P2｜程式品質｜排程發送的三個弱點

- **證據**
  - 鎖不回收：`backend/src/routes/scheduler.ts:51` 設 `processingAt` 後，若行程在發送中被終止，沒有任何地方會把它清掉（全 repo 搜尋 `processingAt`，只有設值與設回 `null`，沒有依時間回收）。該訊息會永遠停在「待發送」但不再被撈到（`:30` 只撈 `processingAt == null`）。
  - 全撈：`:26-31` 的查詢沒有時間條件，每分鐘把所有已核准、未發送的訊息讀回來，再在程式裡比時間（`:39`）。

- **驗收標準**：測試覆蓋「鎖定後當機 → 下一輪能重領且不重複發」、「三群中一群失敗 → 只重試那一群」；查詢的讀取筆數等於到期筆數。

### W-11｜P2｜程式品質｜SIGTERM 處理範圍太大

- **證據**：`backend/src/index.ts:20-30` 把整個 `harnessRuns` 集合中 `queued`／`running` 的文件全部標成 `failed: cloud_run_terminated`，沒有限定是這個實例處理中的任務。

- **建議修法**：每筆 run 記 `instanceId`（或在記憶體維護本實例的 runId 集合），收到 SIGTERM 只處理自己的；另外用逾時（例如 `updatedAt` 超過 5 分鐘）回收真正卡住的。
- **驗收標準**：測試中兩個實例各有一筆 running，對其中一個送 SIGTERM，另一個的 run 狀態不變。
