# WiPPY Agent Hub 規格 v0.2

- 日期：2026-11-04
- 狀態：**已確認**，可以開始開發
- 使用者故事：`docs/specs/2026-11-04-agent-hub-user-stories.md`（本規格的驗收依據）
- 使用者：單一擁有者。另外有 Agent 帳號（Instinct），權限受限
- 開發方式：TDD，每階段一個 PR，疊在前一階段上做（stacked），由使用者 merge

---

## 0. 設計原則

1. **WiPPY 不製作內容。** 網頁、媒體、判斷、回覆都由 Grok Bot 或 Instinct 負責。
2. **WiPPY 只做不需要模型的硬流程**：收訊、存檔、規則比對、派送、驗證、發送、額度控管、重試、稽核。
   - 唯一用到模型的地方是「前處理」（重點整理，見第 5 節），使用者已確認。
   - 前處理有嚴格的次數上限，超過就降級為不整理。
3. **不符合規格就退回給 Agent，WiPPY 不自己修。** 例如網址打不開、格式不對、缺預覽圖：WiPPY 不轉存、不轉檔，回傳結構化的錯誤原因，讓 Agent 自己修正後重送。
4. **安全預設**：群組預設關閉；Agent 權限最小化；每個動作都留稽核紀錄；嚴守額度。

## 1. 外部系統

### 1.1 Grok Bot（已確認可用 Routine webhook 和自訂 MCP）

- **WiPPY → Grok Bot**：POST 到 Routine 的 webhook URL，header 帶 `Authorization: Bearer <key>`，body 是 JSON。
  - 回 200 只代表「已接受」，結果是非同步的。
- **Grok Bot → WiPPY**：
  - **MCP**（Streamable HTTP，`/mcp`）
  - **REST**（`/api/hub/v1`）
  - 兩者都用 `Authorization: Bearer <WiPPY 發給 Grok 的 API key>` 驗證。
- **派送 payload：**
  ```json
  {
    "jobId": "...",
    "callback": { "tool": "complete_dispatch", "restUrl": ".../api/hub/v1/dispatches/{jobId}/complete" },
    "rule": { "id": "...", "name": "...", "instruction": "使用者在規則裡寫的指令" },
    "group": { "id": "...", "name": "...", "memberCount": 10 },
    "digest": { "...": "重點整理（可能是 null）" },
    "messages": ["原始訊息（依規則設定，媒體附簽名連結）"],
    "quota": { "remaining": 0, "agentDailyRemaining": 0 }
  }
  ```

### 1.2 Instinct（後台帳號模式）

- WiPPY **無法主動呼叫** Instinct。
- Instinct 使用一組專屬的 **Email 和密碼**登入 WiPPY 後台（Firebase Auth email/password），**定時進來**處理收件匣。
- Instinct 的所有操作都走網頁 UI，背後呼叫跟 Grok 相同的 Hub 動作邏輯，用同一套守門和稽核。

### 1.3 LINE Messaging API（限制摘要）

- **收**：
  - 文字、圖片、影片、語音、檔案、貼圖、位置都收得到。
  - 媒體只給 messageId，要呼叫 `GET https://api-data.line.me/v2/bot/message/{id}/content` 下載。LINE 會在一段時間後刪除內容，所以**收到就立刻下載**。
  - 影片、語音要先查 `/content/transcoding` 的狀態，還在轉檔就延後重試。
- **發**：
  - 文字、Flex（連結卡片）
  - 圖片：HTTPS，JPEG/PNG，原圖 ≤ 10MB，預覽圖 ≤ 1MB
  - 影片：HTTPS，mp4 ≤ 200MB，必須附預覽圖
  - 語音：HTTPS，m4a，必須附長度（毫秒）
  - **不能發檔案**：一律改成連結卡片。
- **額度**：
  - 用 push 發到群組時，**按群組人數計算**。
  - 免費方案大約每月 200 則（實際以 `GET /v2/bot/message/quota` 和 `/quota/consumption` 為準）。
  - reply 不計額度，但 Agent 的流程是非同步的，大多用不到 reply。

## 2. 架構

```
LINE webhook ─▶ [Ingest] 去重 → groupMessages；媒體 → 下載佇列 → 私有 Cloud Storage
                    │
                    ▼
               [Rules] 即時規則（關鍵字/類型/@bot/訊息量）
                    │  定時規則由 /scheduler/hub-tick 觸發
                    ▼
               [Preprocess] 免費模型整理（全域節流；超出上限就略過）
                    │
          ┌─────────┴──────────┐
          ▼                    ▼
   [Dispatch → Grok]     [Inbox → Instinct]
   Routine webhook         agentInbox 項目
   重試、失敗預警          逾時未處理預警
          │                    │
          ▼                    ▼
   MCP / REST ──────▶ [Hub Actions 核心] ◀────── Instinct 工作台 UI
                       權限 → 守門 → 冪等 → 佇列 → 執行 → 稽核
                         │
                         ├─ LINE 發送服務（額度估算與守門）
                         ├─ agentRecords（紀錄）
                         └─ activityMessages（排程，直接核准）

[Quota Monitor] /scheduler/hub-quota 每小時 → 70% / 90% 預警
[Cleanup]       /scheduler/hub-cleanup 每天 → 刪除超過 180 天的資料
```

### 2.1 佇列與重試

- `JobQueue` 介面有兩種實作：
  - 正式環境：Cloud Tasks
  - 本機和測試：InlineQueue
- 工作類型：`media_download`、`preprocess`、`dispatch`、`action_execute`。
- 重試策略：指數退避，從 10 秒開始，每次 ×2，最長 10 分鐘，**最多 8 次**。
  - 遇到 4xx 錯誤（429 除外）不重試，直接標記 `failed`。
  - 最後一次失敗時，發預警到預警群組，並寫入稽核紀錄。
- 後台可以手動重試失敗的工作。

### 2.2 冪等

- LINE webhook 用 `webhookEventId` 去重。
- 每個 Hub 動作都必須帶 `idempotencyKey`。文件 ID 是 `{agentId}_{key}`，用 create 寫入，已存在就直接回傳先前的結果。
- 所有 LINE 發送都帶 `X-Line-Retry-Key`（UUID），LINE 端也會去重。

## 3. 帳號與權限

| 角色 | 登入方式 | 權限 |
|---|---|---|
| `owner` | Firebase Auth（目前的登入方式） | 全部 |
| `agent` | Instinct：Email + 密碼 | 工作台：讀取開放群組的資料、處理收件匣、執行 Hub 動作。**不能**改設定、Agent、規則、群組開關、帳號 |
| API key | Grok Bot：Bearer token | 跟 `agent` 一樣，只透過 REST 或 MCP |

- `hubAccounts/{uid}`：`{ role: 'owner' | 'agent', agentId?, ownerId, disabled }`。
- 後端用 middleware 解析出「實際擁有者 `ownerId`」和角色，所有查詢都用 `ownerId` 做範圍限制。
- **禁止公開註冊**：
  - 登入頁拿掉「註冊」。
  - 後端只接受 `hubAccounts` 裡有、而且沒被停用的 uid。
  - 擁有者第一次登入時，用環境變數 `OWNER_USER_ID` 綁定為 owner。
- Instinct 帳號由擁有者在後台建立（後端用 Admin SDK 建 Firebase 使用者），密碼只在建立時顯示一次，也可以重設。

## 5. 前處理（唯一用到模型的地方）

- **什麼時候跑**：只有規則設定 `include.digest = true` 時，才在派送前產生重點整理。產生過的摘要可以重用：同一個群組在同一段時間內只整理一次。
- **產出**（模型輸出 JSON）：
  - `summary`：一段摘要
  - `points[]`：問題、待辦，以及提到的日期、時間、地點、金額
  - `tags[]`：分類標籤
  - `imageNotes[]`：圖片說明，只在模型支援圖片輸入時才產生
- **影片、語音、檔案**：不交給模型，用硬流程列出 `mediaList[]`（誰傳的、檔名、大小、連結）。
- **節流**：全域節流（每分鐘 / 每天上限、最短間隔），所有呼叫 LLM 的地方共用，包括現有的活動 AI 對話。
  - 遇到 429：依 `Retry-After` 延後重排。
  - 每天的上限用完：`skipped = true`，直接派送原文，**流程不中斷**。
- **輸出格式錯誤**：不做 repair（不浪費呼叫次數），直接標記為 skipped。

## 6. Hub 動作（Grok 的 MCP / REST 和 Instinct 的 UI 共用）

### 6.1 查詢

| 動作 | 說明 |
|---|---|
| `list_groups` | 開放的群組，以及這個 Agent 被允許的群組 |
| `get_messages(groupId, since?, until?, types?, limit≤200)` | 原始訊息，媒體附簽名連結（7 天有效） |
| `search_messages(query, groupIds?, since?)` | 用硬比對（包含 / 不分大小寫）搜尋，不使用模型 |
| `get_digest(digestId \| groupId+since)` | 只讀取已產生的摘要，**不會**觸發模型 |
| `get_media(mediaAssetId)` | 簽名連結和 metadata |
| `list_records(filter)` | 已存的紀錄 |
| `get_quota` | LINE 本月額度、已用量、Agent 今日剩餘次數 |
| `list_inbox` / `get_dispatch(jobId)` | 收件匣、派送內容 |

### 6.2 執行（都必須帶 `idempotencyKey`）

| 動作 | 硬流程驗證（不通過就退回 `invalid`，並附原因） |
|---|---|
| `send_message(groupId, text)` | 1–5000 字 |
| `send_alert(text, severity)` | 發到預警群組；不受 Agent 每日上限限制，可以動用保留額度 |
| `send_link(groupId, url, title, description?, imageUrl?)` | URL 必須是 https、未登入狀態 GET 回 2xx（只取 header）、不是內網位址。發送 Flex 連結卡片 |
| `send_image(groupId, url, previewUrl?)` | https、2xx、`Content-Type` 是 jpeg 或 png、≤ 10MB。preview 沒給時，原圖 ≤ 1MB 才能拿原圖當 preview，否則要求 Agent 提供 `previewUrl` |
| `send_video(groupId, url, previewUrl)` | https、2xx、`video/mp4`、≤ 200MB；必須提供 preview |
| `send_audio(groupId, url, durationMs)` | https、2xx、`audio/x-m4a` 或 `audio/mp4`；必須提供 durationMs |
| `record(category, title, content, tags?, groupId?, sourceMessageIds?)` | 必填欄位不能空白 |
| `schedule_message(groupId, text, sendAt)` | sendAt 必須是未來時間；寫入 `activityMessages`（`reviewStatus: approved`），歸到每個群組一個「Agent 排程」活動 |
| `complete_dispatch(jobId, summary?)` | Grok 完成一次派送 |
| `complete_inbox(itemId, note?)` | Instinct 處理完一個收件匣項目 |

### 6.3 守門（依序檢查，任何一項不通過就標記 `blocked` 並附原因）

1. Agent 被停用 → `agent_disabled`
2. 目標群組不在 `allowedGroupIds` 內，或群組沒有開啟 `agentEnabled` → `group_not_allowed`
3. Agent 今天的發送次數已達 `dailySendLimit` → `agent_daily_limit`（預警不受此限）
4. 預估會扣的則數（群組人數）超過「剩餘額度 − 保留額度」 → `line_quota_reserve`（預警可以動用保留額度）

**WiPPY 不會自己修正：** 不轉存、不轉檔、不縮圖、不用模型改寫。驗證失敗一律退回，Agent 修正後用新的 `idempotencyKey` 重送。

## 7. 額度監控

- `/scheduler/hub-quota` 每小時執行一次：
  - 查 LINE 的 quota 和 consumption，更新 `hubCounters`。
  - 第一次跨過 70% 或 90% 時，各發**一次**預警（每個月重新計算）。
- 每次發送前估算會扣的則數：發到群組時，用群組人數。人數以 `getGroupMembersCount` 取得，快取 1 小時。
- 儀表板顯示：
  - 本月額度、已用量、預估月底用量（依目前速度推估）
  - 今天的 LLM 用量
  - 每個 Agent 今天的發送次數

## 9. 成本（每月）

**假設：** 5 個群組、每天 300 則訊息、30 張圖、5 個檔案、10 次派送、保留 180 天。

- Firestore：在免費額度內。
- Cloud Storage：只存 LINE 傳進來的媒體，穩定後約 3GB，約 US$0.07。
- 流量：只有 Agent 下載媒體，量很小，約 US$0.1。
- Cloud Run / Tasks / Scheduler：免費。
- 模型：免費。
- **合計：每月不到 US$0.5。**

真正的瓶頸是 LINE 免費推播額度。WiPPY 不轉存 Agent 的內容，所以不會產生成員打開媒體的流量費。

## 10. 分階段（stacked PR，TDD）

| 階段 | 範圍 | 主要自動化測試 |
|---|---|---|
| **P1** 帳號與收訊 | `hubAccounts`、角色 middleware、禁止註冊；群組開關；webhook 去重；所有訊息類型寫入；媒體下載佇列（轉檔狀態、大小上限、重試）；JobQueue 介面 | 角色權限矩陣；未開放群組不派送；各類事件對應的資料；重試與 failed |
| **P2** 發送、驗證、額度 | LINE 發送服務（文字、Flex、圖片、影片、語音、retry key）；URL 驗證；額度估算、守門、監控、預警 | 每種退回原因；守門順序；70% / 90% 各預警一次；預警可以動用保留額度 |
| **P3** 規則、前處理、派送、收件匣 | 5 種觸發與冷卻；LLM 全域節流與降級；digest；Grok Routine 派送與重試；Instinct 收件匣與逾時預警；`/scheduler/hub-tick` | 規則命中與冷卻；429 延後；上限用完時 skipped；派送 payload；逾時預警只發一次 |
| **P4** Hub 動作 API | REST `/api/hub/v1`、MCP `/mcp`；API key；冪等；稽核；`schedule_message` 整合活動排程 | 401 / 403；同一個 key 只執行一次；MCP 工具清單與呼叫；排程訊息經現有 tick 發出 |
| **P5** 後台 UI | 第 8 節所有頁面 | 元件測試：表單驗證、角色可見性、工作台流程 |
| **P6** 收尾 | 清理排程、文件、雲端建置指引（runbook） | 清理範圍正確 |

所有 PR 都開好後，交付 `docs/agent-hub-setup-guide.md`：雲端資源、Grok Routine 和 MCP 設定、Instinct 帳號建立的逐步指引。

## 11. 已確認的決定紀錄

| 題目 | 決定 |
|---|---|
| Agent | Grok Bot（webhook + MCP，已確認可用）、Instinct（後台帳號，第一階段就要做） |
| WiPPY 的角色 | 只做硬流程；內容製作、判斷、修正都交回 Agent |
| 前處理 | 照第 5 節，已確認 |
| 預警 | 發到只有擁有者和 bot 的預警群組 |
| Agent 發訊息 | 不需要核准，但要通過守門檢查 |
| 手動活動 | 維持核准流程 |
| 預設值 | 每日 20 次、70% / 90% 預警、保留 5%、保存 180 天、簽名連結 7 天、檔案上限 50MB、收件匣 24 小時逾時預警 |
| PR | 每階段一個 PR、stacked、使用者 merge |
| 雲端 | PR 都開好後提供建置指引，由使用者操作 |
