## 逐項紀錄

### 前置：讓本分支 push 時也會跑 CI

原本 `ci.yml` 只在 PR、push 到 main 時觸發。這次不開 PR，所以加上 `codex/**` 分支的 push 觸發，才看得到 GitHub 上的結果。

### W-04 關鍵設定與啟動檢查

- `backend/src/config/startupCheck.ts`：正式環境（`K_SERVICE` 或 `NODE_ENV=production`）啟動時，缺必要變數就印一行 WARNING，只列名稱；不會讓服務結束。已在 `index.ts` 的 `listen` callback 呼叫，並包 try/catch。測試：`__tests__/startupCheck.test.ts`。
- 非密鑰設定：`LLM_PROVIDER`、`LLM_MODEL` 移到 `deployment/production.env`，`deploy.yml` 改從那裡讀（值與原本相同）。`NODE_ENV=production` 直接寫在 `deploy.yml` 的 `env_vars`，不放 env 檔，因為該檔會被匯出到 `GITHUB_ENV`，會讓前端 `npm ci` 略過 devDependencies。
- 本輪核對時修了 `startupCheck.test.ts` 一個斷言：env 沒設 `LLM_PROVIDER` 時預設走 `openai_compatible`，缺的不會是 `GEMINI_API_KEY`，測試補上 `LLM_PROVIDER: 'gemini'`。
- 密鑰帶法（`GEMINI_API_KEY`、`HUB_ENCRYPTION_KEY`、`SCHEDULER_SECRET`）完全沒動。
- 沒有加 `CLOUD_TASKS_*`：加了會啟用 Cloud Tasks 路徑，改變線上行為。

### W-07 部署順序與檢查

- 順序改成：Firestore 規則＋索引 → Cloud Run（`no_traffic: true`、`tag: next`）→ 檢查 → 導流量 → 前端 build → Hosting。
- 檢查打的是 tag 網址 `https://next---<CLOUD_RUN_URL 的 host>`（打正式網址只會測到舊版）：`/health` 要 200（重試 5 次）、`/api/hub/me` 不帶憑證要 401（`hubAuth` 缺 Authorization 一律回 401）。
- 檢查失敗 job 就停，新版沒拿到流量，線上維持上一版，所以不另寫回滾。
- 導流量用同一個 action 再跑一次，只給 `revision_traffic: LATEST=100`。這步一定要有，不然 `no_traffic` 會讓之後每次部署都「成功」卻永遠沒上線。
- `push` 加 `paths-ignore: docs/**、**/*.md`（backend／frontend 底下只有 `frontend/README.md` 一個 md，不是執行期檔案）；`workflow_dispatch` 保留，想強制部署可手動跑。
- firebase-tools 改 `npx --yes firebase-tools@15.1.0`，和根目錄 `package.json` 同版。
- 限制：索引這步只是先送出建立請求，大型集合可能還在建，不等它建完。

- 驗證（fb941f3、ef99b11）：刪掉 `backend/src/middleware/auth.ts`。後台 API（groups、activities、broadcast、send-logs、agent）改用 `hub/http/auth.ts` 的 `ownerAuth`（＝`hubAuth({ allow: ['owner'] })`）。「正式環境沒設 `OWNER_USER_ID` 就回 503」也只剩 `rejectWhenOwnerMissing` 一處。
  - 行為差異：非擁有者的 403 代碼從 `not_owner` 變成 `account_not_allowed`（陌生帳號）或 `forbidden`（Agent 帳號）；401 多帶 `code`。前端沒有地方依賴舊代碼。本機沒設 `OWNER_USER_ID` 時，Agent 帳號以前能打後台 API，現在會被擋（比較合理）。

### W-10 排程發送

改在 `backend/src/services/activityScheduler.ts`（W-13 之後排程邏輯搬到這裡），共用規則放 `services/activitySchedule.ts`。

- 不再全撈：排程訊息多存一個 `triggerAt`（和 `triggerValue` 同一個時間點，Firestore Timestamp），查詢加 `triggerAt <= now`、照時間排、一輪最多 200 則。建立、改時間、AI 企畫、Agent 排程四個寫入點都會寫。`firestore.indexes.json` 加了對應索引。
- 鎖逾時：`processingAt` 超過 10 分鐘視為沒人在發，下一輪可重領（log `scheduler_lock_reclaimed`）。改群組時「訊息正在發送」的擋法也只認還沒逾時的鎖，不會被死鎖卡一輩子。
- 部分失敗：每群的結果記在訊息的 `deliveries.<groupId>`（成功／失敗、次數、錯誤），每發完一群就寫。有群失敗時訊息留在待發送，照 Hub 的 `backoffSeconds` 退避後只重發沒成功的群；最多 5 輪，或失敗原因重試也沒用（群組不存在／停用、LINE 回 4xx）就標 `failed`。
- 不重發：每次 push 帶 LINE retry key（由活動＋訊息＋群組算出，沿用 Hub 的 `retryKeyFor`），「LINE 收了但來不及記錄就當機」的那一群重發時 LINE 只收一次（409 視為已送達）。為此排程改用 `line.ts` 新增的 `pushLineText`（新版 SDK client），`e2e/backend.cjs` 的假 LINE 同步接上。
- 上線相容：
  - 新索引還在建時，到期查詢會收到 FAILED_PRECONDITION，這時自動退回舊的全撈查詢（log `scheduler_due_index_missing`），發送不中斷；索引好了就自動走新查詢。
  - 舊訊息沒有 `triggerAt`：排程第一次跑時自動補，之後 24 小時內每 10 分鐘再補一次（接住舊版執行個體還在寫的），然後永久關閉。進度記在 `systemState/activityMessageTriggerAtBackfill`（規則已加，前端讀寫都擋）。
- 測試：原本的 `scheduler.test.ts` 測的是抄在測試檔裡的一份邏輯，不是真的程式，所以刪掉，改成 `activityScheduler.test.ts` 用記憶體版 Firestore 跑真的函式，原本的情境（未到期、未核准、活動非進行中、發送時段）都搬過去了。
- 沒做：前端沒有顯示「哪幾群沒送到／重試中」，重試期間訊息仍顯示待發送；`/api/groups` 的手動發送與廣播仍用舊 client、沒有 retry key（不在這項範圍）。

### W-06：Firebase 端擋掉非擁有者（登入當下就擋）

我假設你平常用 Email 登入，所以主按鈕留 Email，Google 收成頁面下方的小連結（點開會寫「只有擁有者事先加進名單的 Google 帳號進得來」）。如果你其實是用 Google，跟我說，我把兩者對調。
前端沒辦法保證「不在名單的人不會在 Firebase Auth 留下帳號」，要在雲端做：
1. Firebase Console → Authentication → Settings → User actions，關掉「Enable create (sign-up)」，這樣沒被你建過的帳號登入會直接失敗，Auth 也不會多出人。
2. 如果要 Google 登入也只給自己：先在 Authentication → Users 手動加你自己的 Google 帳號（或用 Admin SDK 預建），再配合上面的設定；要更嚴格就用 blocking function（beforeSignIn 比對 `OWNER_EMAIL`），這需要升級 Identity Platform，我沒做。
3. 驗收：拿一個不在名單的 Google 帳號按登入，應該立刻失敗，Users 清單不會多一筆。
